AI Agent 调用手机端侧能力的方案探索（理论篇）

本文件为个人实践前的理论整理，用于分享思路与前期研究。当前尚未实际开发，部分细节可能存在偏差，后续将根据实践更新。
本版已在初稿基础上吸收一轮实践探讨，补充了跨网 ADB 授权、闹钟语义、Shizuku 持久化、轻量桥接（Termux）等要点，并做了信息脱敏。

1. 引言与背景

我们希望让运行在服务器、NAS 或电脑上的 AI Agent（如 OpenClaw、Hermes 等）能够调用手机的某些系统功能，例如设置闹钟、添加日历事件、发送通知等。

一个自然的想法是利用手机厂商自带的端侧 AI（小爱、Siri、小艺等），但厂商通常不开放这些端侧模型的 API 给第三方直接调用。因此，我们需要寻找其他方式，在 Agent 与手机系统之间搭建一座桥梁。

本文总结了两条可行路线：自建 HTTP/MCP 桥接服务 与 ADB + Tailscale 远程控制，并对比它们的优缺点、实现要点及扩展可能性。

2. 核心思路：绕过端侧 AI，直接调用系统能力

手机厂商的端侧 AI 主要负责意图理解，但实际执行动作需要操作系统 API。Agent 本身已经具备意图理解能力，所以我们可以跳过手机端侧 AI，直接让 Agent 调用手机系统提供的接口。

Agent (OpenClaw/Hermes)
│
│  自定义工具 / MCP / HTTP / ADB
▼
手机桥接层（HTTP 服务、MCP Server 或 ADB 接口）
│
▼
Android / iOS 系统能力（闹钟、日历、通知、设置等）

3. 总体架构对比

方案 通信方式 手机端要求 主要优点 主要缺点
HTTP/MCP 桥接 HTTP 请求或 MCP 协议 安装自建 App（或 Termux），常驻前台服务 安全可控、接口定制、稳定、可后台 需开发与维护，功能局限于预先实现的接口
ADB + Tailscale ADB 命令（基于 TCP/IP） 开启 USB 调试、运行 adbd 功能极强，几乎可执行任意 shell 命令，无需开发 安全性较差、重启需重配、依赖网络、跨网需首次授权
Termux 轻量桥接 HTTP / MCP（Python 脚本） 安装 Termux 并后台运行 无需写原生 App，Python 即可，快 shell 权限受限，拿不到系统时钟/日历等深层能力

三种方案可独立使用，也可组合（例如在桥接 App 内调用部分 shell 命令）。

4. 方案一：HTTP/MCP 桥接服务

4.1 Android 实现要点

  • 开发语言：Kotlin（推荐），用 Ktor 或 NanoHTTPD 搭建轻量 HTTP 服务器。
  • 前台服务：为了让服务器长期运行，必须使用前台服务（Foreground Service），并在通知栏显示常驻通知。
  • 系统 API：
  • 闹钟：使用 AlarmManager.setExactAndAllowWhileIdle() 创建应用内闹钟。
  • 日历：通过 CalendarContract 写入系统日历。
  • 接口示例：
  • POST /alarm：参数 time、label，创建一次性闹钟。
  • POST /calendar：参数 title、start_time、end_time 等，添加日历事件。
  • 权限：需要 SCHEDULE_EXACT_ALARM（精确闹钟）、WRITE_CALENDAR（日历写入），并在首次使用时引导用户授权。
  • 安全：建议加 Token 认证（如 HTTP Header 的 Bearer Token），仅监听内网，不暴露公网。

⚠️ 闹钟语义要讲清（实践补充）
用 AlarmManager 设的闹钟是应用内闹钟——到点由你自己的 App 弹广播/通知，它不会出现在系统时钟 App 的闹钟列表里。如果想要"接近系统时钟"的效果，折中方案是触发 ACTION_SET_ALARM intent：手机弹出系统设置的闹钟界面并把时间预填好，用户只需点一下确认。这属于"自动到预填 + 手动确认"，比完全手动强，但要接受这一下点击。

4.2 iOS 实现要点

由于 iOS 系统限制，无法像 Android 一样运行常驻 HTTP 服务器。更可行的方式是利用快捷指令（Shortcuts）作为桥接层：

  • 在快捷指令中创建"添加日历事件""添加提醒事项"等操作。
  • 通过 URL Scheme（shortcuts://run-shortcut）或第三方工具（如 Pushcut）触发。
  • 若 Agent 运行在 Mac 上，可用 shortcuts run 命令行直接调用快捷指令（通过 iCloud 同步）。
  • 闹钟无法完全自动创建，可改用"提醒事项"，或打开时钟 App 让用户手动设置。

4.3 轻量替代：Termux（无需写原生 App）补充

如果不想写 Kotlin，可用 Termux（无需 root）在手机上跑一个 Python HTTP 服务 / MCP Server 充当桥接层：

  • 覆盖场景：本地通知、简单的闹钟/提醒、HTTP 回调、执行 shell 命令等。
  • 优点：不用开发、不用编译，Python 脚本即可，技术栈低，迭代快。
  • 局限：Termux 进程是 shell 用户，拿不到系统时钟/日历、通知使用权、无障碍等深层权限。因此它适合"轻量/快速验证"，长期稳定的核心能力仍建议走原生 App。
  • 保活：配合 Termux:Boot 或 wakelock / 前台会话维持运行。

4.4 与 Agent 集成

  • 若 Agent 支持自定义工具，可将其注册为 HTTP 工具，指向桥接服务的 URL。
  • 若支持 MCP（Model Context Protocol），桥接层可暴露为 MCP Server，提供标准化工具接口。
  • 对于 Hermes 这类框架，可订阅特定主题并触发手机端动作。

5. 方案二：ADB + Tailscale 远程控制

5.1 解决无线调试限制

Android 11+ 的"无线调试"功能要求手机连接 WiFi（多数国产 ROM，尤其华为/荣耀，没连 WiFi 时开关直接置灰）。若手机未连 WiFi（例如使用移动数据），可通过以下步骤绕过：

  1. 用 USB 数据线连接手机和电脑，开启 USB 调试。
  2. 执行 adb tcpip 5555，使 adbd 进程监听 TCP 5555 端口。
  3. 断开 USB，手机保持网络连接（移动数据或 WiFi 均可）。
  4. 在手机和 NAS/服务器上安装并登录 Tailscale，组成虚拟局域网（手机在任何网络下都拿到固定的 100.x 虚拟 IP）。
  5. 在 NAS 上通过 Tailscale 分配的 IP 连接：adb connect <手机TailscaleIP>:5555。

⚠️ 两个实践坑（补充）
- 重启失效：service.adb.tcp.port 不带 persist 前缀，手机重启后 adbd 会恢复 USB 模式，需要重新 USB 连一次。想持久：非 root 手机可用 Shizuku（开源、无需 root 提权）写入持久化 persist.service.adb.tcp.port，重启后 5555 仍开启，还能远程触发。
- 跨网首次授权：每次新设备/新环境跨网连接，手机会弹一次"允许 USB/网络调试"授权（RSA 指纹校验）。未授权时 adb connect 会显示 offline 或 failed to connect。这是 Android 安全机制，Shizuku、tcpip 都绕不开；授权一次后后台常驻即可。

5.2 ADB 与 HTTP/MCP 的功能对比

维度 ADB 调用 HTTP/MCP 桥接
功能范围 几乎无限，可执行任意 shell 命令、模拟点击、改系统设置、装应用 局限于预先实现的工具接口
灵活性 极高，适合临时、探索性任务 较低，但满足常用自动化
安全性 风险较高，shell 权限可能被滥用 更可控，可最小化权限并加认证
实现难度 无需开发 App，掌握 adb 即可 需开发并安装桥接 App
稳定性 依赖网络与 adbd，重启后需重配 前台服务保活，较稳定
权限要求 默认 shell 用户，部分操作需 root 或特殊授权 正常应用权限申请，无需 root

结论：ADB 适合技术验证和高度自定义场景；HTTP/MCP 方案适合长期稳定、安全要求较高的家庭自动化。

6. 桥接 App 可实现的扩展功能

若采用 HTTP/MCP 桥接，除闹钟和日历外，还能实现：

  • 通信类：发送短信、拨打电话、读取联系人（需相应权限）。
  • 系统设置：切换 Wi-Fi/蓝牙、调节音量/亮度、手电筒、勿扰模式等。
  • 媒体控制：播放/暂停、下一曲、调节媒体音量。
  • 应用管理：打开应用、查询已安装应用列表。
  • 位置与传感器：获取当前位置、读步数、光线等传感器数据。
  • 通知管理：发送本地通知、读取其他应用通知（需通知使用权）。
  • 文件操作：读写公共目录或应用私有目录。
  • 高级自动化：通过无障碍服务模拟点击/滑动、读取屏幕内容（需用户开启无障碍）。

这些大多可后台执行，但涉及敏感权限（短信、通知读取、无障碍）需用户一次性授权，部分操作可能弹确认框。

7. 后台运行与权限考量

  • Android：要让桥接服务长期运行，必须用前台服务（Foreground Service），通知栏显示常驻通知。Android 8.0+ 对后台服务限制严格，前台服务是保活关键；Android 13+ 需 POST_NOTIFICATIONS 权限。
  • 权限申请：每项功能都要在 Manifest 声明并在运行时动态请求。建议首次启动时引导用户一次性授予必要权限。
  • iOS：因系统限制无法长期后台运行 HTTP 服务，快捷指令更适合一次性触发。

8. 安全注意事项

  • 认证：HTTP 桥接服务应加 Token 或 Basic Auth，避免局域网内其他设备滥用。
  • 网络隔离：仅监听内网，不暴露公网；若用 Tailscale，确保 ACL 正确配置。
  • 最小化权限：只暴露真正需要的功能，降低攻击面。
  • 加密：条件允许时用 HTTPS（自签名证书）。

10. 总结

让 AI Agent 调用手机系统能力是可行的，关键在于建立一个中间桥接层。本文梳理了两条主路线：

  • 自建 HTTP/MCP 服务（含 Termux 轻量版）：稳定、安全、可控，适合长期使用与常用自动化。
  • ADB 远程控制（配合 Tailscale 固定 IP）：强大、灵活、易配置，适合技术验证与高自定义场景。

两者各有适用场景，可独立或结合使用。本阶段仅为理论梳理，后续进入实践验证，会持续更新。
